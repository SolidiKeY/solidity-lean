# Coordinator tools

gate.sh runs from the current checkout: `gate.sh per-file FILE...`, `gate.sh touched`, `gate.sh checkpoint`, or `gate.sh full`. It writes one status line per gate and `gates.tsv` plus individual logs under `GATE_LOGS` (default a temporary `coord-gates` directory). It also writes `HEAD` (the commit the gates ran on), which handoff.sh checks. The build gates: `touched` builds the touched modules' reverse import closure within the `Solidity` library, plus touched example and TestSuite files, and their dependents too when the touched files include `Syntax`, `Semantics` or `Calculus` (or `GATE_EXAMPLES=1`); `checkpoint` adds `lake build Solidity`, `lake build SolidityExamples SolkeyTestSuite` under the same condition, and the script checks; `full` runs `run-lean.sh` (every default target and the TestSuite) instead, and the corpus, TestSuite and automation checks. `GATE_BASE` selects the touched comparison base (default `origin/master`); touched modules are the Lean files changed since its merge-base with HEAD, renames counted as delete plus add, plus untracked files, and their reverse import closure. Relative FILE and `GATE_LOGS` paths are taken from the caller's directory. Exit 0 means all gates passed, 1 means at least one failed, and 2 means invalid usage or setup.

The merge pre-gate is `bash scripts/coord-tools/gate.sh touched`, run on the
prospective merged checkout before committing or updating the shared branch.
Touched, checkpoint and full modes run `node scripts/check-layers.mjs` before any
build and stop immediately on failure, even if no Lean file was touched. A failed
layer check is never a SIGBUS retry candidate. Full mode also retains the existing
internal layer check in run-lean.sh; per-file diagnostics are unchanged. This
script checks the candidate tree and does not perform or publish a merge.

`seal.sh DIR [BASE]` creates a bundle of BASE..HEAD (default `origin/master`; when BASE is not an ancestor of HEAD, its merge-base with HEAD is the recorded base), a manifest, and SHA256SUMS, then verifies the seal. `seal.sh --verify DIR` checks file inventory, hashes, bundle tip, that the bundle's prerequisites are the manifest base or its ancestors (the base itself among them), and pack integrity. It uses `TMPDIR` for the temporary indexing repository. Exit 0 indicates success; nonzero indicates invalid usage, an empty range, or verification failure.

`handoff.sh [NOTES-FILE]` writes HANDOFF.md and CLOUDVM-RESULT.json and prints the JSON result. Set `HANDOFF_OUT` for the output directory (default `$TMPDIR/coord-handoff-<head>`, outside the checkout), `HANDOFF_BATCH`, `HANDOFF_SLUG`, `HANDOFF_BASE` (default origin/master), `HANDOFF_STATUS` (default partial), `HANDOFF_CHECKPOINTS` (comma-separated name=status), and `HANDOFF_GATES` (colon-separated gate log directories). Exit 0 means written; nonzero means invalid inputs or a refused done status. Done requires passing gates and a clean tracked tree, and is refused when a gate directory's `HEAD` (written by gate.sh) is not the current HEAD.

`disk.sh [--free]` reports free disk and cgroup memory. `--free`, or free space below `DISK_MIN_FREE_BYTES` (default 2 GiB), removes exited containers, extra worktree builds (only a real `.lake/build` inside the worktree, never one reached through a symlink), and older verified seals only; a seal directory holding a file that SHA256SUMS does not list is kept. Without cgroup files the ram line reads `unavailable`. Set `DISK_REPO`, `DISK_CGROUP`, and colon-separated `DISK_EVIDENCE_ROOTS` to choose the repository, cgroup and evidence roots. Exit 0 means the report/cleanup completed; nonzero means invalid usage or an error.

`try-tactics.sh MODULE GOAL [CANDIDATE...]` checks the standard tactics followed by supplied candidates against a proposition file or the type of a declaration name. With the lake backend it writes scratch files outside the checkout (`TMPDIR` chooses their parent); the mcp backend needs a temporary `TerraTry*.lean` at the checkout root, removed on exit (a killed run can leave it). It prints one result and log path per attempt; a candidate that leaves `sorry` FAILs. `TRY_TACTICS_BACKEND` selects the backend (lake, mcp, or auto). Exit 0 means at least one passed, 1 means none passed, and 2 means invalid usage or, with none passed, a lean-mcp bridge error.

`lean-mcp start|stop|status|tools|call TOOL JSON|diag FILE|goal FILE LINE|try FILE LINE TACTIC...` maintains a checkout-specific MCP daemon, starting it on demand. `LEAN_MCP_SOCKDIR` chooses its socket directory, `LEAN_MCP_SERVER_CMD` overrides the server command, `LEAN_MCP_IDLE` sets idle seconds (default 7200), `LEAN_MCP_TIMEOUT` the client wait per call (default 1800 s), and `LEAN_MCP_START_WAIT` the start wait (default 600 s, the first start may install lean-lsp-mcp). The daemon serves one request at a time; `status` prints `busy` while a call runs, and a client that disconnects early does not stop the daemon. Exit 0 means success, 1 means a failed tool/diagnostic or no successful tactic, and 2 means a bridge or usage error. Stop the daemon after use. `try-tactics.sh` uses the bridge when `TRY_TACTICS_BACKEND=mcp`, or with auto when the daemon is running.

`register.sh [--check] [MODULE...]` regenerates the library roots (`Solidity.lean`, `Bridge/SolidityBridge.lean`) from the file tree: each imports every module under its source prefix, sorted, minus other libraries' subtrees and `Solidity/Scratch/`. A lane runs it after adding, moving or deleting a module and commits the result; the integrator regenerates the roots after a merge instead of resolving their hunks. MODULE arguments are only checked to exist. `--check` writes nothing and lists missing or extra imports. Exit 0 means the roots are current (or were rewritten), 1 means `--check` found a stale root, and 2 means invalid input or another error.

`module-map.py [BASE]` lists the Lean modules added since the merge-base with BASE (default `origin/master`) that have no row in `docs/module-map/*.md` or its fragments, each with the lane's fragment `docs/module-map/<area>.d/<lane>.md` of the area whose rows share the longest directory prefix and a draft row from its docstring. Exit 0 means every added module has a row, 1 means rows are missing, and 2 means a usage or setup error.

`fragments.sh [--check | --resolve [--lane NAME] [--ours-lane NAME]] [--force]` regenerates `docs/module-map.md`, `docs/module-map/*.md`, `docs/README.md`, `TERRA-TODO.md` and `scripts/g07-axiom-pins.json` from the fragment directory next to each (`X.d/`; see `docs/parallelism.md`, "Shared registries"). `--check` exits 1 on a stale file. The write exits 1 instead of dropping lines a combined file has that no fragment produces, unless `--force`. `--resolve`, during a conflicted merge or on a merge commit, adopts each side's direct edits of a combined file into that lane's fragment (lane name from MERGE_HEAD's branch or the merge message, or `--lane`), regenerates, runs `register.sh`, and stages; exit 1 means a path stays conflicted. Exit 2 is a usage or setup error.

`ship-cache.sh [--dry-run] CHECKOUT` relays master's Lake artifacts from CHECKOUT (an integration checkout at `origin/master` whose gates just ran) to the active lane VMs (`SHIP_LANES`, default the lanes `poll-state.json` marks online) through `~/.local/share/cloudvm-coord/vmexec.py` (`--put`/`--get`, sha256-verified): to each VM the artifacts it lacks, extracted with `--skip-old-files`, and the input lines it lacks, appended under Lake's lock; Mathlib cache files (`SHIP_MATHLIB_SUMS`) to a VM with the Bridge's Mathlib checkout at the host's pin and no Mathlib build. A VM short of disk for pack, contents and `SHIP_RESERVE` (2 GiB) is skipped. Shipments and receipts are under `SHIP_STATE` (default `~/.local/state/cloudvm-coord/cache-ship`). Exit 0 means every VM is current or skipped with a reason, 1 means a transfer or verification failed, and 2 means a usage or setup error. Lanes do nothing: after merging master, `lake build` fetches the shipped modules (`docs/parallelism.md`, P5).

`coord-ask [-t TITLE] TEXT` (or TEXT on stdin) asks the coordinator a question from a lane checkout. It needs only `git push`: it pushes a one-file commit (`coord/questions/<ts>.md`, on top of `COORD_Q_BASE`, default `origin/master`) to `coord-q/<lane>/<ts>`, without touching the working tree, index or lane branch. The workflow `.github/workflows/coord-question.yml` turns it into a GitHub issue labelled `question` (lane, head, batch and slug in the body) and deletes the ref. Exit 0 means pushed; nonzero means empty input or a failed fetch or push.

`coord-evidence [-m NOTE] PATH...` archives lane evidence (receipts, logs, timings, handoffs, checksum manifests, resource and validation records) in the private coordination repository `SolidiKeY/solidity-lean-coord` (`COORD_EVIDENCE_REPO`), under `evidence/<batch>/<slug>/<PATH>`; an absolute PATH is stored under its basename. It needs only `git push` (rebasing and retrying when lanes push at once), refuses files over 50 MB (keep those on the VM and cite path and sha256), and does not touch the lane checkout. Cite its output line `evidence: <commit> <dir>` in the result. Evidence never goes in the code branch: `scripts/check-evidence-files.sh` rejects it in CI and in every gate. Evidence that was committed here before 2026-11-07 is in that repository under `archive/solidity-lean/<original path>`, so older documents that cite such a path refer to it there.
