## 2. Lean errors

The calldata `Loc` constructors (`cdBytes`, `cdString`, `cdArray`,
`cdFixedArray`) and the slice stride `STy.cdStride`, added to
`Source/Eval.lean` by the Codex lane on the base branch, left these modules
failing; all are fixed here:

- `Source/Preservation/Combinators.lean` (`MemPres.readLoc'`): each new arm
  is `hl.elim` (`LocOK` is `False` on them).
- `Source/Preservation/Reads.lean` (`readLoc_keep`),
  `Lowering/Readonly/LocationEffects.lean` (`readLoc_effect`,
  `writeLoc_effect`, `indexLoc_effect`) and
  `Yul/Views/RetainedLocationRun.lean` (the `cases` and the raw `Loc.rec`):
  arms for the new constructors.
- `Source/Horizon.lean` (`indexLoc_grow`, `indexLoc_const`): the calldata
  branch of `indexLoc` was a `match σ with` (auto-generalized over the value
  and its proof) that `split` cannot take apart. It now calls the total
  function `cdIndexLoc off i σ`, with the same arms and results, so the branch
  is one `pure`; the Horizon tactics close it unchanged.
- `Lowering/V08/SliceFailureLowering.lean` (`accepted`, `beyond`): the stride
  was stated as the literal `1`/`32`. `STy.sliceable` admits
  `array .calldata σ none` with `0 < σ.cdStaticWords`, whose stride is
  `σ.cdHeadBytes` (`32·k` for a static-array element), so the literal was
  false there. The statements now say `τ.cdStride`, which is the old literal on
  bytes, string and one-word-element arrays and what `sliceR` computes on
  every type. This changes another lane's statement (a correction, not a
  weakening). `Yul/Adapters/SourceSliceFrame.lean` unfolds `cdStride` in one
  `simp`.

Module-map rows were also added for five `Backend/Executable/Constructor*`
modules that the inherited Codex work left without one.

## 3. G43: compiler success and the payment relation

**Finding.** In the core fragment `transfer_sim` never produces
`StmtOut.refused`: the typed run's `State.canPay` is exactly the machine's
balance check and `accepts` (`Sim.funds`, `Sim.oracle`), so both refuse the
same payments and both revert. The refused-payment outcome of
`compile_correct` and `Compilation.Agrees` is only propagated by the
compound lemmas, never created. The joint world/payment relation G43 asks
for is therefore the one `Sim` (and `Compilation.Input` on the core path)
already carries; the memory paths admit no payment.

**Theorems** (new modules; nothing in `Evm/` edited; no frozen statement,
premise or exclusion changed):

- `Backend/Payments/CoreExact.lean`: `stmt_paid`/`prog_paid` re-run
  `stmt_sim`/`prog_sim` with `pays` fixed at `false`, using `transfer_paid`
  (`transfer_sim` at `pays = false`) and flag-generic `ite_flags`,
  `call_flags`. Headlines: `compile_paid` (`compile_exact` without its
  `Prog.pays P = false` premise), `compile_success` (OBL-SUCCESS on the core
  path), `compile_revert`, and `compile_storage_paid` (`compile_storage`
  without payment outcomes, from `Sim.init`, which also shows the premises
  satisfiable).
- `Backend/Payments/CompilerExact.lean`: `Compilation.AgreesExact`
  (`Agrees` without the two payment disjuncts), `correct_exact` for every
  `Compilation` result under its `Input`, `agrees_of_exact`,
  `compile_success` (the separate compiler-success theorem, H62/H69) and
  `revert_exact`.

**Consumers.** `Theorems.compiler_correct`/`compiler_checked` and
`Compilation.correct` keep their frozen statements; a consumer that needs no
payment asymmetry uses `correct_exact`/`compile_success` instead. Replacing
the frozen headlines would be a versioned pair (H57), not done here.
