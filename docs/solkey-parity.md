# solkey parity: what `sol_wp` proves of the KeY corpus

Does the Lean wp verifier discharge the same assertions KeY does?

Every proof obligation of the four solkey suites was ported and run through
`sol_wp`. The corpus is generated by `scripts/solkey-port.mjs` from
`~/projects/solkey/keyext.solidity.examples` (the `.sol` suites) and
hand-written for the two `.key` suites; verdicts are produced by
`./scripts/check-solkey-parity.sh` and pinned in `tests/solkey/expected.tsv`.

## Result

| suite | obligations | proved | open | unsupported |
|---|---:|---:|---:|---:|
| `TestSuite.sol` (taclet suite) | 176 | 155 | 12 | 9 |
| `solc/SolcExpressions.sol` | 20 | 20 | 0 | 0 |
| `solc/SolcStructs.sol` | 11 | 9 | 0 | 2 |
| `solc/SolcArrays.sol` | 12 | 11 | 1 | 0 |
| `solc/SolcMemory.sol` | 11 | 9 | 0 | 2 |
| `solc/SolcMappings.sol` | 9 | 7 | 2 | 0 |
| `solc/SolcControlFlow.sol` | 10 | 7 | 3 | 0 |
| `net/*.key` | 20 | 3 | 0 | 17 |
| core `RulesTest` `*.key` | 41 | 7 | 0 | 34 |
| **total** | **310** | **228** | **18** | **64** |

**228 of the 246 obligations that are expressible in this fragment are
proved**, kernel-checked, with no `native_decide` — including the whole of
`SolcExpressions`, `SolcStructs`, `SolcMemory`, the `net` machinery, and
155 of the 167 ported taclet tests. (`Examples/Solkey/Net.lean` carries a
fourth theorem, an iterated transfer, that is not itself a solkey PO and so
is not counted.)

## How to read the three verdicts

- **proved** — `sol_wp` closes the judgment. The proof is symbolic execution
  checked by the kernel; the axiom profile is
  `[propext, Classical.choice, Quot.sound]`.
- **open** — the obligation is ported but `sol_wp` does not close it. The
  reason is recorded per row in `expected.tsv`.
- **unsupported** — no theorem exists, because the obligation is outside the
  fragment. The reason is recorded per row.

## Two ways the port is weaker than KeY

These are properties of the approach, not of individual tests, and they
apply to obligations counted as *proved*:

1. **Concretization.** KeY proves box-tagged functions over *unconstrained*
   program variables; `sol_wp` evaluates from one concrete store. A
   `require(x == 5 && y == 7)` becomes `uint x = 5; uint y = 7;`, so the
   same assertion is checked *at one instance* rather than universally. 23
   obligations are marked this way in the `note` column, with the witness.
2. **`require`s are made true rather than assumed.** Because the port turns
   every judgment into a *diamond*, it proves more than KeY's box in one
   respect — the program must also not revert — and less in another: a box
   over an unsatisfiable `require` is vacuously valid in KeY, and such a
   judgment would report "proved" while proving nothing. Storage-bound
   `require`s (`require(1 < values.length)`) are therefore discharged by
   emitting the `push`es that establish them.

## The 64 unsupported obligations

| reason | count |
|---|---:|
| core `RulesTest`: term-level heap-algebra identities and KeY loader/taclet tests, not program judgments | 34 |
| `net` invariant POs: uninterpreted `CInv` over a symbolic ledger, booked against `msg.value`/`msg.sender` | 12 |
| `new T[](n)` memory-array allocation is not in the fragment | 11 |
| `transferWithCallback` has a relational meaning (`CallbackSemantics.lean`) but no surface syntax | 4 |
| field-name overloading: `Depth0.recursive` and `Depth1.recursive` differ in type, and `SoliditySyntax.fieldTy` is one global name→type table | 2 |
| `msg.value` is not in the `sol_expr` grammar | 1 |

The 34 `RulesTest` entries are not a coverage hole in the calculus: they
assert things like `selectSt(storeSt(mtSt, balance, 10), balance) = 10`,
which `RuleValidation.lean` and `RuleSoundness.lean` cover directly.

| family | count | members |

| two-dimensional arrays | 3 | `storageMatrix{WriteRead,NseIndex}`, `matrixElementWriteRead` |

| local storage-alias binding | 3 | `storageLocalDeclSkip`, `storagePushLocalBind`, `testStorageNestedPushReturnAlias` |

| other | 3 | `testDeepPopDoesNotResetMappingMember`, `testStorageEvaluationOrder`, `nestedIfElseSelectsBranch` |

All but two report `` `simp` made no progress ``, which is the signature of a
*missing entry in the evaluation battery* rather than of a calculus gap: the
verdict metavariable cannot be assigned, so `sol_wp_step` stops peeling. Each
of the fixed families below had exactly that shape, so these are likely to
fall to the same treatment.

## What the exercise found

Running the corpus surfaced eight defects that the pre-existing 15-example
suite did not, all now fixed:

1. **`a.length` was unimplemented.** `SVal.find` had no arm for a
   `Seg.field "length"` on an array, so *every* solkey assertion about an
   array length was unprovable. This is the one genuine semantic gap the
   exercise found (`Semantics.lean`).
2. **`BinOp.retTy`/`isArith`/`UnOp.retTy` missing from the battery** — any
   binary operation assigned to a *storage or memory* place (as opposed to a
   stack variable) silently stopped mid-block.
3. **`IncDec.isIncrement`/`isPre`/`binOp` missing** — every `x++`/`x--`.
4. **`ternaryExpr` missing** — every `c ? t : e`.
5. **`pushPlaceExpr`/`pushPlace`/`PlaceExpr.expr` missing** — every
   `push`/`pop`.
6. **`SVal.defaultOf.defaultOfFields` missing** — every `delete` on a struct.
7. **`expandSolPlace` had no arm for a parenthesized expression**, so
   `(e).push(…)` parsed but had no elaboration function.
8. **The `{pre,post}decrement` taclet family was unwritable** in surface
   syntax: `--` cannot be a Lean token. Added as `predec(e)`/`postdec(e)`.

Two further findings are about the *cost model* rather than correctness, and
matter for anyone extending the fragment:

- **The name tables are on the hot path.** `SoliditySyntax.rootExpr`,
  `rootPlace` and `storageOriginFor` are matches on the variable name that
  every judgment elaborates. Widening them with seven contracts' state
  variables roughly doubled the cost of elaborating *any* judgment and put
  the pre-existing proofs over their `whnf` budget — a budget that
  `set_option maxHeartbeats` does not raise for these elaborations. The port
  therefore keeps the ported schemas *out* of those tables, via the
  `name@@Type` form (`SoliditySyntax.globalExpr`), whose cost is independent
  of how many contracts are ported.
- **The store is scanned per access.** It is an association list, so its
  length multiplies the cost of every proof; hence one store per contract
  (`State.testSuiteStore` and the stores after it) rather than one union.

## Reproducing

```bash
node scripts/solkey-port.mjs        # regenerate the corpus from solkey
./scripts/check-solkey-parity.sh    # verdicts vs tests/solkey/expected.tsv
./scripts/check-solkey-parity.sh --only 'Solc*'    # iterate on a subset
./scripts/check-solkey-parity.sh --update          # re-pin expected.tsv
```

The corpus is its own Lake target (`SolidityCorpus`) and is deliberately
not imported by `Solidity.lean`: it is a few hundred `sol_wp`
proofs, and folding it into the default build would make every ordinary
`./run-lean.sh` pay for the whole parity suite.

A caution learned the hard way: the harness treats any `lean` exit code other
than 0 or 1 as fatal. An OOM-killed module emits no diagnostics, and "no
diagnostics" must never be read as "everything proved" — it silently reported
a module of 167 failing theorems as fully proved.
